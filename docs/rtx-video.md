# RTX Video Super Resolution

超分采样新增 50% 档位，输出 1920×1080 时传输 960×540。宽高各减半，像素数为原生的 25%；目标码率仍由用户设置，不会自动减少到四分之一。默认原生 100% 保持不变，分辨率与超分均不修改被控端 Windows 显示设置。

控制中心可分别选择采样比例和超分算法。RTX Video Super Resolution 使用 NVIDIA 驱动的视频处理器；FSR 1 仍可选择，也用于 RTX 不可用时的兼容回退。两端需要支持相同采样比例的新版本。算法只在控制端运行，被控端无需开启 NVIDIA 视频增强。

## 驱动条件与失败处理

控制端需要 Windows、支持该功能的 NVIDIA RTX 显卡和驱动，并在 NVIDIA 控制面板的“视频 → 调整视频图像设置 → RTX 视频增强”中启用超分辨率，或使用 NVIDIA App 中对应的视频设置。Elink 不安装驱动、不下载 NGX 模型、不自动修改系统全局设置。

驱动接受扩展调用并不表示神经网络已运行。每次创建处理器时，Elink 先以生成的亮度细节图比较关闭和开启后的输出，记录 `rtx_probe_mae`。没有可测差异时拒绝标记 RTX 已生效，回退 FSR 1 并显示错误。该探针用于发现静默无效，不是对任意驱动内部算法的鉴定；每次连接会有一次初始化开销。诊断详情保存在性能报告的 metadata 中。

## 显示链路

```text
D3D11VA 解码后的 CPU YUV 平面
→ 原生 NV12 上传
→ D3D11 VideoProcessor + NVIDIA VSR 扩展
→ D3D11 / OpenGL 共享 BGRA 纹理
→ 现有 GPU 播放器及独立统计、光标叠加
```

正常播放不把超分结果下载成 RGB 或 QImage。解码仍存在 GPU → CPU 平面回读，随后再上传，因此整个链路不是零拷贝。`rtx_submit` 是 CPU 调用耗时，`rtx_gpu` 是异步 D3D11 上下文时间戳；它不保证覆盖驱动内部全部跨引擎工作，不能单独视为神经网络总耗时，两者也都不是操作到显示的总延迟。质量自动时由驱动决定具体处理策略。

接口依据为 [Chromium 的 NVIDIA VSR 调用](https://chromium.googlesource.com/chromium/src/+/main/ui/gl/swap_chain_presenter.cc)。使用 D3D11 视频处理接口和 WGL_NV_DX_interop，不要求替换成 D3D12。构建需要 Visual Studio C++ Build Tools、Windows SDK 和 CMake：

```powershell
.venv/Scripts/python.exe -m scripts.build_video
```

生成的 `elink_video.dll` 随便携目录发布。CI 编译此库，单元测试使用替身；真实显卡测试在本地解锁桌面运行。打包验证还要求原生窗口颜色、全屏切换、真实 H.264/D3D11VA 串流、实际 RTX 输出差异和 FSR 回退提示通过。

## 50% 对比方法

```powershell
.venv/Scripts/python.exe -m scripts.compare_upscalers
```

脚本生成桌面文字、纹理与 HUD、斜线三个 1080p 场景，以 20 Mbps / 90 FPS 的 NVENC 编码并用 D3D11VA 解码。FSR 与 RTX 使用同一份解码后 540p 图像，原生 1080p 作为另一基线。报告 RGB PSNR、亮度 SSIM，并生成原图与放大图的像素对齐裁剪对比。只保存合成内容，不保存个人桌面画面。

画质读回与评分不计入性能测试。脚本另外依次运行原生、50% FSR、50% RTX 三轮分进程 WebRTC 回环，分别记录采集、编码、解码和绘制提交。无法达到目标帧率的 95%、算法静默回退或输出没有变化时，脚本报错，不产生通过结论。

超分无法保证恢复 540p 已丢失的小字笔画和色度信息，RTX 也不保证每个场景都优于 FSR 或原生。这不是 FSR 3、帧生成或游戏引擎内的时域重建。静态图指标不等于游戏主观质量，同机回环也不等于 WAN 或与游戏争用 GPU 的表现，发布后仍需两机手动验收。

## 本机画质对比

2026-10-20，RTX 4070 SUPER、驱动 591.86，NVIDIA 视频超分启用、质量自动。三种算法使用同样的 NVENC / D3D11VA、20 Mbps / 90 FPS 设置。表中原生传输 1080p，FSR 与 RTX 均传输同一份 540p 解码图；指标相对未压缩的 1080p 合成原图计算，越高越接近参考。

| 场景 | 原生 PSNR / SSIM | 50% FSR PSNR / SSIM | 50% RTX PSNR / SSIM |
| --- | --- | --- | --- |
| 桌面文字 | 32.61 dB / 0.9979 | 24.16 dB / 0.9446 | 26.75 dB / 0.9769 |
| 纹理和 HUD | 31.51 dB / 0.9865 | 25.21 dB / 0.9326 | 26.05 dB / 0.9369 |
| 斜线 | 31.52 dB / 0.9970 | 23.44 dB / 0.9396 | 25.64 dB / 0.9642 |

三组 RTX 指标均高于 FSR，但原生仍最好。像素对齐裁剪中，RTX 减少了部分文字边缘的毛刺与 FSR 锐化痕迹，小字号仍明显不及原生；50% 档位不应作为追求文字清晰度时的默认值。真实游戏运动、色度和时间一致性不能由这些静态图推断。画质读回和显示验证顺序执行，避免同时启用两个 VSR 处理器导致驱动自动策略让第二路失效。

同机分进程 WebRTC、标准运动图，预热 3 秒后分别测量 15 秒，结果如下。实际屏幕约 75 Hz，FPS 为绘制提交，不是物理扫描或新增游戏帧。

| 模式 | 编码 / 解码 / 提交 FPS | 解码 P50 | 绘制调用 P50 | 提交间隔 P99 |
| --- | --- | --- | --- | --- |
| 原生 1080p | 89.80 / 89.80 / 89.80 | 1.90 ms | 0.54 ms | 12.46 ms |
| 50% + FSR | 89.99 / 89.99 / 89.99 | 0.73 ms | 0.59 ms | 12.65 ms |
| 50% + RTX | 89.99 / 89.99 / 89.99 | 0.73 ms | 0.93 ms | 12.61 ms |

三轮正式测量区间均无解码错误、解码队列或邮箱丢帧；目标码率仍约 20 Mbps。RTX CPU 提交 P50/P95 约 0.74/1.20 ms，D3D11 时间戳 P95 约 1.64 ms，仅用于该场景观测，不代表 RTX 在游戏争用时的固定开销。首次性能测量因窗口短暂不可见判为无效，未计入此表，失败记录保留。

真实窗口验证还通过五种像素格式/颜色组合、全屏切换、统计和光标叠加、空闲不持续重绘、H.264/D3D11VA 串流以及 RTX → FSR、GPU → CPU 两类故障回退。有效对比原始报告位于忽略目录 `.artifacts/rtx50-comparison-20261020/`；不随源码提交。
