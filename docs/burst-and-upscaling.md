# 发送突发、GPU 采集与空间超分

日期：2026-10-16。默认保留原生 100% 分辨率、用户目标码率与帧率，不修改被控端系统显示设置。GPU 采集优化独立于控制端是否使用 GPU 显示。

## 依据与实施顺序

1. [WebRTC pacing](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/pacing/g3doc/index.md) 使用发送节奏和有限的临时加速来处理队列。Elink 旧发送器只有平均速率与 4 ms 额度，大帧发送会阻挡后续发送。先增加有界突发，并让音频、RTCP 绕过视频等待；不通过丢弃任意 H.264 参考帧来掩盖卡顿。
2. [Salsify, NSDI 2018](https://www.usenix.org/conference/nsdi18/presentation/fouladi) 说明编码大小、发送预算和网络反馈需要协作。Elink 增加大帧、发送耗时、RTCP 恢复请求与完整帧到达间隔的事件记录，避免仅从状态栏瞬时 Mbps 推断根因。
3. [AMD FSR 1](https://github.com/GPUOpen-Effects/FidelityFX-FSR) 提供适合截图/视频输入的 EASU + RCAS。使用其 MIT 头文件，在现有 GPU 显示链路中接入；没有使用需要游戏运动矢量、深度与抖动信息的 FSR 3.1，也没有补帧。
4. [FFmpeg D3D11 scaler](https://github.com/FFmpeg/FFmpeg/blob/n8.0/libavfilter/vf_scale_d3d11.c) 与桌面复制可在回读前缩放和转换。当前 FFmpeg 只允许 NV12/P010，未显式设置视频处理器颜色矩阵/范围，且复制 RGB 色彩标记。必须校验转换与 H.264 VUI，不能直接照搬源标记。

## 发送与拥塞

平均 RTP 预算仍为媒体预算的 1.08 倍，用于头部等开销；平均额度最多允许约两帧，限制在 8–32 ms。短时峰值为该 RTP 预算的 1.25 倍，峰值额度最多 4 ms。平均和峰值约束同时生效，空闲不会积累无限额度。RTX 也扣同一预算，但有独立等待锁；音频及 RTCP 不排在视频等待锁之后。输入数据通道不经过此视频 hook。

单次码率超标不降档，不改变用户设置。接收端 RTCP 报告持续出现丢包至少 3%，或 RTT 比已见最低值增加超过 40 ms，持续至少 1.5 秒且距上次调整至少 2 秒时，有效媒体预算下调 20%，最低 300 kbps；干净反馈持续 3 秒后按目标码率的 10% 逐步恢复。检测到拥塞即收紧临时峰值。REMB 的已观察流量仍不能作为空闲桌面的链路容量。

这是保守反馈策略，尚不是完整 GCC/BBR。线路切换、Wi-Fi 争用、持续丢包和真实路由器队列仍需两机测试。编码预算变化会重建编码器并产生 IDR，至少 2 秒一次，可能有短暂开销。峰值不是测得的可用带宽，算法不会硬性预留公网带宽；DSCP 仍由系统、路由器、Tailscale 路径决定是否保留和优先处理。

## 采样与呈现

“串流分辨率”为输出尺寸；原生 100% 为编码尺寸等于输出尺寸。75% / 66.7% 均对宽和高分别取比例，编码尺寸向下对齐偶数。例如 1920×1080 的 66.7% 传输 1280×720，再在控制端 GPU 上重建到 1920×1080。1440p 的同档为 1706×960；对齐造成的极小宽高比差异按输出比例显示。

66.7% 的像素数为原生约 44.4%，75% 为 56.25%。固定目标 20/30 Mbps 不变，因此不会自动节省同等比例的网络流量；降低了转换、编码、解码和上传的像素处理量，也可由用户手动选择较低码率。小字、细线和色度细节可能损失，FSR 不能恢复全部原始信息。没有实测依据声称超分画质胜过原生。

FSR 需两端新版本和控制端 GPU 显示，使用实际 OpenGL 4.2+ 能力，仍保留已修正黑屏的 3.3 兼容上下文请求。无支持时给出错误并回退 CPU 显示，回退仍收到已协商的较低尺寸，应选原生 100% 后点击“应用”恢复原生质量。窗口仍可等比例适配；不修改系统分辨率、缩放或显示刷新率。

## GPU 采集边界

Windows 默认尝试 `ddagrab → scale_d3d11 → hwdownload(NV12)`，外部 FrameClock 控制节奏；高 source ceiling 避免 FFmpeg 的粗粒度 Sleep 压低 90 FPS。没有把采集计数当作独立桌面更新数。

启动时从同一帧分支取得 GPU NV12 与 RGB 参考，用区域均值对比四种 601/709、有限/全范围组合；避免文字边缘的缩放核差异干扰。要求颜色信息和匹配置信度足够，不能通过时自动回退 DXCam，不从分辨率或显卡型号猜矩阵。只在初始化时额外下载 RGB；不保存或上传桌面像素。光标模式变化需重建采集图。屏幕访问、驱动或滤镜失败也回退，并给出提示。

编码器接收 NV12 并写入测得的颜色信息，后端或颜色变化会重建编码器。仍有 GPU→CPU 回读及 NVENC 输入上传，控制端 D3D11VA 也仍可能回读；这不是零拷贝。

## 验证方法

回归覆盖瞬时/持续拥塞、恢复、RTCP 适配、编码预算生效、峰值和平均包络、RTX 计费、音频/RTCP 优先、采样协商、旧端拒绝、偏好保存、采集回退和光标切换。打包自检要求原生、两档 FSR 的真实窗口像素、软件/硬件解码串流、FSR GPU 查询以及三档 D3D11 采集经编码/解码的颜色验证通过。

```powershell
.venv/Scripts/python.exe -m scripts.check_gpu_video --stream-check --frames 20
.venv/Scripts/python.exe -m scripts.benchmark_matrix --source desktop --capture-backend auto --output .artifacts/native-matrix
.venv/Scripts/python.exe -m scripts.benchmark_matrix --source desktop --render-scale 67 --output .artifacts/fsr-matrix
```

本机回环与自动测试不能证明用户两机的偶发卡顿已消除，也不能证明与游戏争用 GPU 时没有性能影响。显示器约 75 Hz，高于此值的提交可包含重复帧，不代表屏幕扫描或输入到显示延迟。实际用户网络仍需升级两端后手动验收，并在复现卡顿后导出性能报告。

## 本机实测

RTX 4070 SUPER，同机分进程、20 Mbps、NVENC / D3D11VA / OpenGL，解锁桌面。完整预设矩阵每项预热 2 秒、测量 6 秒，实际主屏 1920×1080 / 74.973 Hz；1440p/4K 输出来自放大主屏，不是原生 4K 采集。桌面内容未标准化，不能将与旧报告的差值全部归因于一个组件。

33 个允许组合完成有效窗口测量，正式区间无解码错误，30 个达到比较线，脚本因 3 项未达标返回非零。26 项触发兼容采集，说明 GPU 校准在灰暗/文字桌面的适用率仍有限；不能把超分描述成所有组合都更快。720p/900p/1080p 的 240 FPS 项主要受 DXCam 读取/CPU 转换限制。原生矩阵与超分矩阵的场景不标准化、回退次数不同，不能直接用表格差值测 FSR 成本；异步 GPU 查询的 1080p/4K 超分 P50 分别约为 0.097/0.343 ms。

标准化 1080p90 运动纹理，修改前后各测 15 秒：平均提交约 89.59 → 89.80 FPS，绘制间隔 P99 约 15.92 → 12.73 ms，均无正式区间解码错误。分位数为最近 600 样本的窗口值，不能当作全部用户环境的保证；这两轮没有模拟真实 WAN 拥塞。虚拟时钟回归以相同 70×1200 字节的大帧验证新发送器耗时低于旧单预算算法的 80%，并同时验证平均/峰值包络。

单独的 1080p90、66.7% GPU 采集回环，15 秒内平均提交约 89.99 FPS、20.006 Mbps、无解码错误或队列丢帧；NV12 采集/回读 P50 约 0.88 ms，FSR GPU P50 约 0.098 ms。该轮采集内容与 DXCam 对照未标准化，不能宣称所有桌面都可达到相同结果。超分选择不保证 GPU 采集能通过校准；失败时兼容回退可能成为新的瓶颈。
