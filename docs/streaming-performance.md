# 串流性能测量与 GPU 显示原型

90 FPS 调度问题的最新诊断、论文/开源资料、实施计划和修改前后实测见 [帧率修复计划与验证](frame-rate-plan.md)。下文保留前几轮的实现记录和测量边界。

2026-10-14 开发记录。实现阶段先完成修改、测试和 Git 同步；随后用户明确授权将本阶段成果打包为 0.4.22 Preview。合成实验结果不代表双机游戏验收完成。

## 使用

启动 0.4.22 便携版，或源码启动：`.venv/Scripts/python.exe main.py`。连接后，在控制中心选择“导出性能报告…”保存 JSON。新主机提供 `performance-v1` 能力，可同时导出两端的统计；旧主机不提供时仍能导出控制端数据。请求失败记录错误类型，会话发生变化则取消导出，避免混合两个会话。

在画质设置中选择“GPU 纹理显示（实验）”，应用并重新连接。默认“兼容显示（CPU）”保持现有显示路径。显示方式会保存，GPU 上下文、格式、颜色矩阵或绘制失败时自动回退 CPU，并在窗口给出提示。无 OpenGL 的 offscreen/minimal 测试环境直接回退。

GPU 选择独立于解码器：软件 H.264 解码也可用 GPU 显示；D3D11VA 解码也可用 CPU 显示。简洁状态栏保持原样，详细测量只进入导出报告。

## 报告口径

每个会话重置，线程安全；每阶段保留最近 600 个样本，最多 32 个计时阶段。P50/P95/P99 使用排序后 nearest-rank，`total` 是会话累计次数，`samples` 是当前窗口样本数。按包计时的窗口比按帧计时的窗口短，不能直接当作同一段时间的总量。

| 阶段 | 测量含义 |
| --- | --- |
| `capture_read_cursor` | 读取桌面像素、查询/叠加光标的 CPU 墙钟耗时 |
| `capture_convert` | 构造 AVFrame、缩放与转换 YUV420P |
| `capture_deadline_late` | 采集工作线程相对绝对时间槽的迟到量；`capture_slots_missed` 另统计跳过的时间槽 |
| `capture_to_encode` | 本机从采集调用开始到进入编码的时间，包含前两项，不可重复相加 |
| `encode` | 编码调用时间，第一帧可能含编码器初始化 |
| `encoded_media_time` | 编码帧字节数除以当前媒体码率预算，单位 ms；不是编码耗时 |
| `send_frame` | 上一帧交给发送循环到它请求下一帧的墙钟耗时 |
| `encode_ahead_wait` / `encoded_queue_wait` | 发送循环等待预取编码完成 / 已编码帧就绪后等待被取走 |
| `rtp_pacer_wait` | 单个 RTP 包进入发送限速器到允许发送的等待，含锁等待 |
| `rtp_send_call` | 单个 RTP 发送调用耗时，不等于数据到达网卡或对端的时间 |
| `assembled_frame_interval` | 完整编码帧进入解码队列的间隔，不是 RTP 重组耗时 |
| `decode_queue_wait` | 完整编码帧入队到开始解码 |
| `decode` | 解码调用，可能包含硬解帧回读；未分离 GPU 执行时间 |
| `decoded_queue_wait` | 解码结束到接收协程取得帧，包含线程/事件循环交接 |
| `prepare_display` | CPU 模式的 BGR 转换与线程调度；GPU 模式的格式选择/必要转换 |
| `mailbox_wait` | 图像进入最新帧邮箱到 GUI 取出 |
| `qt_scale` / `cpu_paint_total` | CPU 缩放、整个 CPU paintEvent（后者包含前者） |
| `texture_upload_call` / `gpu_paint_submit` | 纹理上传调用、GPU paintGL 的 CPU 提交时间（后者包含前者） |
| `gui_schedule_to_paint` | GUI 取出帧到提交该帧，含窗口调度和部分绘制 |
| `capture_interval` / `encode_interval` / `present_interval` | 对应本机事件的间隔；present 是提交绘制，不是屏幕实际亮起 |

队列计数包括解码队列清空/等待 IDR 时丢弃的帧、解码后队列覆盖、GUI 邮箱覆盖、解码错误。它们是本地处理丢帧，不能当作网络丢包率。`encoded_frames` / `decoded_frames` / `presented_frames` 用于比较阶段处理量。

各阶段有重叠，不可把所有 P95 相加。不同主机的时钟从不相减；RTT 仍是网络往返测量。报告没有单向网络时延、RTP 首包到完整帧重组时间、GPU 完成时间、扫描输出时间或输入到显示的完整延迟。

## GPU 路径与边界

当前原型为：PyAV 解码 → CPU 可访问的 YUV420P/NV12 平面 → OpenGL R8/RG8 纹理 → shader 颜色转换与缩放 → Qt 合成。GPU 路径绕过 `to_ndarray(BGR)`、QImage 包装和 CPU QImage 缩放，持有 AVFrame 直到上传完成；支持 padded stride、BT.601/709 和有限/全范围。

Qt 自带 OpenGL 能力，无新增第三方图像库。它是 GPU 呈现原型，尚未接入 D3D11 解码纹理共享、原生交换链或端到端零拷贝。D3D11VA 的 GPU→CPU 回读仍可能发生。编码仍为 H.264/YUV420P；没有恢复色度采样时丢失的文字边缘，不应宣传已解决所有毛糙。

色块实验发现，PyAV 在源/目标颜色矩阵同时继承 BT.709 时会得到错误的 RGB 转换；兼容路径明确指定 RGB 转换目标参数及源范围，使已标记的 709/全范围内容与 shader 一致。使用独立公式测试，不用同一个错误转换结果作为自己的期望值。

Qt 顶层合成上下文与子 OpenGL 控件均请求 `swapInterval=0`。仅给子控件设置该参数时，本机出现约 16.7 ms 的额外提交等待；补齐顶层默认格式后该等待在实验中消失。桌面合成器、驱动和显示器仍决定实际显示时间，这不是屏幕刷新率修改，也不是保证驱动遵从请求。

## 开发验证

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m scripts.check_gpu_video --frames 120
.venv/Scripts/python.exe -m scripts.check_gpu_video --frames 30 --stream-check
```

第二条在真实 Windows 桌面弹出临时置顶的合成画面窗口，不注入系统键鼠、不构建 EXE。正确性检查读取测试窗口覆盖的屏幕区域，并核对 Qt 内部画面；屏幕像素只在内存中使用，不保存或上传截图，计时区域不做 GPU 回读。请保持桌面解锁且不遮挡测试窗口。第三条还验证本机合成 H.264/WebRTC 串流的软件解码和 D3D11VA 解码显示，硬解不可用时检查失败。结果在忽略目录 `.artifacts/gpu-video-check.json`，不要提交个人会话报告。

本机样例：1080p 合成输入、1280×760 窗口、桌面 60 Hz、预热 10 帧后测 120 帧；统计栏关闭。不包含采集、编码、网络和解码。

| 指标 | CPU 兼容路径 | GPU 纹理路径 |
| --- | ---: | ---: |
| 准备至绘制调用 P50 | 8.94 ms | 0.93 ms |
| 准备至绘制调用 P95 | 11.18 ms | 1.27 ms |
| 120 帧进程累计 CPU 时间 | 2.97 s | 0.17 s |
| 120 帧墙钟时间 | 1.02 s | 0.12 s |

进程 CPU 时间包含多线程，所以可大于墙钟时间。这是单次合成 CPU 提交测试，不能解释成 GPU 实际渲染完成时间、游戏 FPS 或双机端到端延迟。5 组颜色/范围/格式检查的 RGB 每通道最大误差为 1–2/255；全屏往返后的保留画面也通过检查。自动测试另覆盖真实本机 WebRTC 报告、会话隔离、GPU AVFrame 交接、队列覆盖计数、偏色回归、偏好保存和 CPU 回退。

下一步仍需在两台机器使用相同动态画面、尺寸、码率和解码器对比，收集两端报告；再决定是否默认启用、改为原生 D3D11 表面共享，并独立验证 input-to-photon。网络拥塞和编码质量优化属于后续阶段；本轮不改变用户目标码率/帧率优先策略。

## 2026-10-15 GPU 黑屏修复

用户反馈 CPU 显示正常、GPU 纹理显示黑屏，两端均为 RTX 4070 Super。本机复现了原实现的绘制问题：在同一个 OpenGL 控件内先画视频，再用 QPainter 画状态文字/软件鼠标，会留下 `GL_INVALID_OPERATION`（1282）；下一帧将该错误报告为上传失败并触发回退。最初检查关闭了状态栏且只读取视频 framebuffer，遗漏了正常使用时的叠加与 Qt 合成路径。

改为 OpenGL 控件只绘制视频，独立透明 QWidget 绘制状态文字和软件鼠标，由 Qt 合成；叠加层不接收鼠标、不抢焦点。父窗口绘制不再触发视频子控件更新，避免合成时产生重复重绘；视频有新帧时提交，叠加内容按需刷新。GPU 真正失败时同时移除两层并恢复 CPU 显示及错误提示。

桌面回归覆盖默认开启的状态栏、连续帧、F10 显隐、软件鼠标显隐、全屏往返、控制菜单和空闲重绘次数，并检查播放器合成后的像素。5 组格式/颜色矩阵/范围的 RGB 最大误差为 1–2/255。本机真实 Client/HostServer 的合成 1080p60 H.264/WebRTC 串流分别通过软件解码（YUV420P）和 D3D11VA（NV12）的连续显示、合成像素及注入绘制故障后的 CPU 回退检查；旧绘制实现作为对照能复现 1282 错误。

上述验证使用本机合成视频，不代表两台机器的游戏帧率、网络表现或用户环境已验收。修复阶段完成源码、测试和 Git 同步后，用户明确授权将修复打包为 0.4.23 Preview，供两端更新后手动验收。

## 2026-10-15 实际窗口输出黑屏复查（0.4.24）

0.4.23 用户反馈仍然整个播放器全黑，但 F8 弹出菜单正常。源码正常连接流程同样复现：解码、纹理上传和绘制计数增长，Qt 内部 `QWidget.grab()` 得到正确画面，实际屏幕上的播放器仍全黑。之前的内部截图与 EXE 的默认 CPU 自检不足以判定 GPU 窗口真正显示成功。

使用仅包含标签和纯红色 QOpenGLWidget 的最小程序隔离配置，得到以下本机对照结果：请求 OpenGL 3.0 时整个客户区全黑，swapInterval 改为 1 仍黑；请求 3.3 CompatibilityProfile 时标签和红色画面均正常。3.0 不具备 3.2 起才定义的兼容模式配置，该机器实际返回 3.0 NoProfile；3.3 请求返回 4.6 CompatibilityProfile。Elink 改用 3.3 兼容配置后，窗口实际输出与内部像素一致。可确定直接触发因素是旧上下文配置；不能仅凭该实验断定 Qt/驱动内部的具体缺陷。

回归改为先读取测试窗口覆盖的实际屏幕区域，再读取 Qt 内部画面；Windows 的窗口 DC 抓取在全屏切换后可能返回旧尺寸内容，因此原生输出检查使用桌面上的对应矩形。旧版绘制代码在新检查中被拒绝（最大颜色误差约 239/255），修正版通过五组格式/色彩检查、状态和软件鼠标显隐、全屏往返，以及软件 H.264/D3D11VA 本机串流显示。失败回退仍保留。

新增冻结程序 `--self-test-gpu <report.json>` 入口。打包必须执行该 GPU 实际显示检查，发布验证收据必须包含原生像素和两种解码串流结果，避免仅凭 CPU 自检发布 GPU 改动。测试需要解锁的 Windows 桌面和可用 D3D11VA，结果仍不替代用户双机验收。
